What it is

Kelir is a birthday capsule: a sender writes a message and adds photos, voice notes or video. It is emailed at 00:00 in the recipient's time zone, and the recipient opens it as a 3D gift. Four pieces do the work:

  • Sender app (frontend/src/pages): make, schedule and edit capsules.
  • API (backend/app/routes): FastAPI; the sender's side is capsules.py, the recipient's is recipient.py.
  • Delivery loop (backend/app/delivery): wakes on a timer, delivers what is due and sends the email.
  • 3D opening (frontend/src/reveal3d): three.js scene the recipient sees.

One action, followed: "Send now"

Stop 1. The sender saves it: create_capsule

backend/app/routes/capsules.py, search async def create_capsule. It checks the email domain, works out deliver_at (due_now), claims the uploaded files, copies the sender's name onto the capsule and commits. If deliver_at <= now (Send now, or a birthday already begun) it starts run_tick as a background task instead of waiting for the timer.

Stop 2. The delivery loop: _deliver_due, _claim_emails, run_tick

backend/app/delivery/scheduler.py. _deliver_due flips scheduled to delivered for capsules whose time has come; _claim_emails picks delivered capsules with no emailed_at, makes a fresh link secret (only its hash is stored) and leases the row. Both use FOR UPDATE SKIP LOCKED, so two loops never double-send. run_tick sends the email after the database commit and records success, or a retry with back-off. delivery_loop calls it every scheduler_interval_seconds; main.py starts it in lifespan.

Stop 3. The recipient opens the link: open_capsule then Reveal3D

The emailed link loads frontend/src/pages/RecipientCapsule.tsx, which calls api.capsuleAccess then api.openCapsule (frontend/src/api.ts) and renders Reveal3D (frontend/src/reveal3d/Reveal3D.tsx). On the server, open_capsule in backend/app/routes/recipient.py only reads; the capsule becomes opened when the page reaches the open box and calls POST /opened (mark_opened → _mark_opened), which is conditional so the first time is the one kept.

To change this, start here

  • When a capsule becomes due: due_now in backend/app/engine/schedule.py (called from create_capsule).
  • Email wording or layout: birthday_email in backend/app/delivery/email_templates.py; texts per language in email_copy.py.
  • Retry timing or attempts: retry_delay, MAX_SEND_ATTEMPTS, SEND_LEASE at the top of scheduler.py.
  • What the recipient's page receives: capsule_out in routes/recipient.py and RecipientCapsule in frontend/src/api.ts.
  • The 3D opening: frontend/src/reveal3d/; stages.ts orders the steps, GiftScene.tsx is the scene.
  • A new column on a capsule: backend/app/models.py plus an Alembic migration in backend/alembic/ (see the next section for why this matters).

A practice to reuse: decide when a copied value freezes, then pin it with a test

Decision. A capsule shows the sender's name. First it was read through a join, so renaming yourself changed already-made capsules. The first fix froze the name at delivery, but a capsule stays editable until opened, so the real question was which moment. It now freezes when the capsule is saved: sender_name is set once in create_capsule and no edit schema accepts it.

Evidence. The entry "Renaming yourself rewrote the name on capsules already made" in devpost/learnings.md, and backend/tests/test_sender_name_frozen.py, which renames before delivery, after delivery, and after an edit, and checks the email, the recipient page and the sender's list.

Reuse. Whenever something you hand to another person shows a value that can change later, name the moment it stops changing before building, copy it onto the thing at that moment, and write the test as "change the source, then check every place it shows".
